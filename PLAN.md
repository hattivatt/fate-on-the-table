# План разработки модуля `chars-to-table`

Модуль Foundry VTT, который выносит персонажа из чарника на стол (канвас сцены) в виде набора объектов `Drawing` + `Tile`, позволяя разместить его перетаскиванием мыши и автоматически синхронизируя с изменениями актёра.

Система: **только `fate-core-official`**. Foundry: **v14** (минимум `14.354`).

## Роадмап

1. **FP-менеджер** — функционал `foundry_macro/fp_manager.js` (детальный план ниже):
   - управление FP игроков и мастера из интерфейса модуля;
   - FP игроков отображаются в уже существующем блоке `fatePointTokens` виджета персонажа, без создания второго ряда жетонов;
   - отдельный сценовый ряд жетонов FP мастера, размещаемый и перетаскиваемый как группа;
   - настройки изображения, размера и шага жетонов;
   - «Новая сцена» (сброс быстротечного стресса, перенос ситуативных аспектов, установка FP мастера);
   - синхронизация с источниками данных Fate Core и с виджетами на активной сцене.

2. **Менеджер ситуативных аспектов** — функционал `foundry_macro/sit_aspects.js`:
   - диалог управления аспектами (добавить/переименовать/удалить, призывы ±);
   - виджет-список аспектов на сцене (Drawing, синхронизируется со сценой);
   - взаимодействие с системным флагом `fate-core-official.situation_aspects`.

3. **Настройки** — расширение `settings.js` до полноценного раздела:
   - темплейт, масштаб, снап, шрифт-оверрайд, цвет текста (есть);
   - изображение FP-жетонов (есть);
   - настройки для фич 1–2 (пути изображений, дефолты, цвета);
   - перенос «журнальных» настроек из `mac_settings.js` в штатные настройки модуля.

4. **Альтернативные лейауты** — набор шаблонов в `layouts.js`:
   - Default (текущий), Minimal (без блока FP/подписей), Wide, NPC (без навыков) и т.п.;
   - выбор лейаута при размещении (по умолчанию — из настроек);
   - регистр лейаутов (публичный API для будущих модулей).

За рамками роадмапа (оценка позже): `challenge.js`, `mac_settings.js` (полный перенос), `init_players.js`, `ad-hoc_roll.js`.

## Детальный план следующей фичи — «FP-менеджер»

Статус: **не начата**.

Цель фичи — перенести управление Fate Points из `foundry_macro/fp_manager.js` в
модуль, не дублируя уже реализованный ряд FP в виджете персонажа и не смешивая
состояние Fate Points с геометрией виджета.

### 1. Зафиксировать контракт данных

До написания интерфейса определить и использовать один источник истины для
каждого типа FP:

- FP игрока: `actor.system.details.fatePoints.current`.
- Refresh игрока: `actor.system.details.fatePoints.refresh`.
- FP мастера: существующий системный флаг
  `fate-core-official.gmfatepoints` на активном GM-пользователе. Использование
  этого ключа сохраняет совместимость с исходным макросом.
- Ряд FP игрока: документы `Tile` с частью `fatePointTokens` внутри обычного
  actor-widget. Их количество уже вычисляется через `@fatePointTokens`, а
  `WidgetSync` умеет создавать и удалять недостающие документы.
- Ряд FP мастера: отдельная группа документов с флагами модуля:

  ```js
  flags["chars-to-table"] = {
    widgetId,
    part: "gmFatePointTokens",
    index,
    ownerType: "gm"
  }
  ```

- Реестр GM-группы на сцене: флаг модуля, например
  `scene.getFlag("chars-to-table", "gmFatePointWidget")` со структурой
  `{ widgetId, anchor: { x, y } }`.
- В GM-группе не должно быть `actorUuid`: это позволит отличать её от
  actor-widget и не пытаться обновлять несуществующего актёра.

Старые флаги тайлов из макроса (`core.fatePointTrackerPlayer` и
`core.gmFatePointTracker`) автоматически не удалять и не включать в управление:
это чужие документы, и их безусловное удаление может уничтожить ручную
разметку сцены. Совместимость на первом этапе сохраняется только для системного
флага FP мастера.

### 2. Разделить ответственность по коду

Предполагаемая структура изменений:

- `scripts/FatePointManager.js` — GM-only диалог, изменение значений,
  refresh, «Новая сцена» и команды синхронизации.
- `scripts/FatePointSync.js` — чтение FP мастера, построение/синхронизация
  отдельного GM-ряда, поиск его документов и очистка осиротевшего реестра.
- `scripts/WidgetBuilder.js` — оставить FP игрока частью общего actor-widget;
  вынести/переиспользовать общую логику построения горизонтального ряда тайлов,
  чтобы GM-ряды не реализовывали второй вариант `tileRow`.
- `scripts/WidgetSync.js` — экспортировать безопасную немедленную синхронизацию
  актёра либо добавить публичный метод, который менеджер сможет вызвать после
  изменения FP, не полагаясь только на debounce.
- `scripts/PlacementManager.js` — обобщить placement-flow так, чтобы он принимал
  не только актёра, но и произвольный набор документов с callback регистрации.
  Существующий `PlacementManager.place(actor)` оставить оболочкой для текущего
  поведения.
- `scripts/widgetDrag.js` — для `ownerType: "gm"` обновлять anchor в флаге
  сцены, а для actor-widget сохранить текущее обновление actor-флага.
- `scripts/settings.js` — зарегистрировать размеры и шаг FP-жетонов.
- `scripts/module.js` — подключить хуки синхронизации, GM-инструмент и очистку
  слушателей.
- `languages/{en,ru}.json` — весь текст менеджера, уведомления и названия
  настроек.

Не создавать отдельный механизм для визуального FP игрока: это приведёт к двум
независимым рядам жетонов и рассинхронизации с `fatePointTokens` в раскладке.

### 3. Синхронизация FP игроков

1. Получать список актёров Fate Core, которыми владеет хотя бы один не-GM
   пользователь. Сортировка должна быть стабильной: имя владельца, затем имя
   актёра и id как tie-breaker. Не ограничивать список тремя слотами старого
   макроса.
2. В диалоге показывать имя, `current`, `refresh` и признак наличия виджета на
   активной сцене. Актёр без размещённого виджета всё равно может быть изменён,
   но менеджер должен явно показывать, что визуального ряда на сцене нет.
3. «Дать» увеличивает `current` на 1.
4. «Забрать» уменьшает `current` на 1, но не ниже нуля.
5. После изменения актёра дождаться обычного `updateActor`-синка и, для
   мгновенного отклика менеджера, вызвать публичную синхронизацию текущей сцены.
   Все виджеты этого актёра на активной сцене должны обновиться, а anchor и
   пользовательские перемещения должны сохраниться.
6. «Синхронизировать всех» пересобирает actor-widget'ы текущей сцены и
   отдельный GM-ряд, но не создаёт новые actor-widget'ы без явного размещения.
7. «Рефреш всех» поднимает `current` до `refresh`, только если текущий запас
   меньше refresh. Значение выше refresh не уменьшать — это поведение исходного
   макроса и позволяет вручную выдать дополнительные FP.

### 4. Синхронизация FP мастера

1. Выбрать активного GM так же, как исходный макрос: первый активный пользователь
   с `isGM`. Если активного GM нет, менеджер должен показать предупреждение и не
   создавать/удалять жетоны.
2. «Дать» и «Забрать» изменяют `fate-core-official.gmfatepoints`, не допуская
   отрицательного значения.
3. `FatePointSync` ищет GM-документы по `widgetId` из реестра сцены и
   синхронизирует количество тайлов с текущим значением флага:
   - создаёт недостающие тайлы одним batch-запросом;
   - удаляет лишние по `index`/стабильному порядку, а не случайно найденные
     документы;
   - обновляет texture, width, height и координаты при изменении настроек;
   - при нулевом значении оставляет реестр и anchor, но не оставляет тайлов.
4. Если текущий FP мастера больше нуля, но все документы GM-группы удалены
   вручную, считать виджет удалённым и очистить его запись в scene-флаге; не
   воссоздавать его автоматически без повторного размещения. При текущем
   значении `0` отсутствие тайлов является нормальным состоянием, поэтому
   registry и anchor сохраняются.
5. Если при положительном значении удалена только часть документов, восстановить
   недостающие документы по сохранённому anchor при следующей явной синхронизации.
6. Подключить синхронизацию:
   - после изменения GM-флага (`updateUser` или явный вызов после операции);
   - при `canvasReady`;
   - после смены настроек FP-жетонов;
   - по кнопкам «Синхронизировать всех» и «Новая сцена».

### 5. Размещение и перемещение GM-ряда

1. В менеджере добавить отдельное действие «Разместить FP мастера».
2. Использовать тот же DOM-based preview из `PlacementManager`, что и для
   персонажа: следование за мышью, снап к сетке, левый клик — подтверждение,
   ПКМ/Esc — отмена.
3. В preview показывать реальный размер ряда и рамки, вычисленные из текущего
   числа FP, размера тайла и шага. Не использовать старые абсолютные координаты
   `gmX/gmY` из журнала как обязательную геометрию.
4. При commit создать GM-тайлы с единым `widgetId` и записать anchor в
   `scene.flags["chars-to-table"].gmFatePointWidget`.
5. Не создавать GM-группу повторно, если на сцене уже есть запись. Вместо этого
   предложить «Переразместить» или удалить старую группу после подтверждения.
6. Расширить `widgetDrag`: перетаскивание любого GM-тайла должно сдвигать весь
   ряд и обновлять scene anchor. Синхронизация через `charsToTableSync` не должна
   запускать рекурсивное перетаскивание.
7. Добавить явное действие «Убрать FP мастера со сцены» с подтверждением.

### 6. Настройки жетонов

Уже существующее `fatePointImage` оставить общей настройкой для player-widget и
GM-ряда. Добавить в штатный раздел настроек:

- ширина тайла, по умолчанию `70`;
- высота тайла, по умолчанию `70`;
- горизонтальный шаг/питч, по умолчанию `20`;
- при необходимости вертикальный шаг, по умолчанию `0`, только если формат
  `tileRow` будет расширен до произвольного направления.

Текущие `w`, `h` и `step` в `layouts.js` использовать как defaults конкретного
лейаута, а настройки — как runtime override. При изменении размера или шага:

- пересчитывать размеры и координаты рядов в actor-widget;
- пересчитывать GM-ряды;
- не менять anchor виджета;
- не оставлять старые тайлы, если новое число/геометрия их больше не требует.

Рамку `fatePointsFrame` не оставлять жёстко несогласованной с настройками:
либо вычислять её ширину по фактическому ряду плюс padding, либо явно
зафиксировать минимальную ширину и расширять её при переполнении.

Если изображение FP не задано, не создавать пустые Tile-документы. Менеджер
должен показать понятное уведомление о необходимости выбрать изображение, а
числовые значения FP при этом всё равно должны изменяться корректно.

### 7. Интерфейс и доступ

1. Добавить GM-only инструмент «Менеджер Fate Points» в scene controls либо
   другой штатный вход модуля, не требующий ручного запуска исходного макроса.
2. Основной диалог повторяет полезную структуру `fp_manager.js`:
   - общие действия: синхронизация и refresh;
   - строки игроков: текущие/refresh и кнопки `+`/`−`;
   - секция мастера: текущее значение, `+`/`−`, размещение/удаление ряда;
   - отдельная кнопка «Новая сцена».
3. Для не-GM не показывать операции управления GM, массовый refresh и
   «Новую сцену». Синхронизация уже размещённых actor-widget'ов должна работать
   по существующим правилам разрешений.
4. Все операции должны быть защищены от повторного клика во время batch-update,
   а ошибки выводиться в console с контекстом и через `ui.notifications`.

### 8. «Новая сцена»

Операция должна сначала показать диалог и только после подтверждения выполнять
изменения. При отмене ни один документ, актёр или флаг не меняется.

1. Показать количество игроков/начальное значение FP мастера.
2. Загрузить `scene.flags["fate-core-official"].situation_aspects`, если флаг
   существует, и предложить список аспектов для переноса. Сохранить выбранные
   записи без изменения их `name` и `free_invokes`.
3. Не удалять рисунки аспектов поиском по тексту `startsWith`, как делает старый
   макрос. До реализации `sit_aspects` изменять только системный scene-флаг и
   вызвать расширяемый hook/событие для будущего менеджера аспектов.
4. Установить FP мастера равным указанному количеству игроков и синхронизировать
   GM-ряд.
5. Очистить на текущей сцене только быстротечный стресс у актёров токенов:
   `box_values` сбросить в `false`, связанный аспект стресса очистить. Остальные
   типы стресса не менять.
6. Разделить обновления обычных Actor и embedded Token по API Foundry v14;
   повторяющиеся токены одного актёра не должны приводить к лишним конфликтующим
   обновлениям.
7. После завершения вывести итог: FP мастера, число перенесённых аспектов,
   количество изменённых треков и результат синхронизации.

Сброс текущих FP игроков в этой операции не выполнять: для этого существует
отдельный «Рефреш всех» и это соответствует поведению исходного макроса.

### 9. Порядок реализации

1. Добавить константы GM-флага, ключей scene registry и частей документов.
2. Вынести повторно используемое построение `tileRow` и покрыть его проверками
   count `0`, count `N`, отсутствующего изображения, scale и изменённого размера.
3. Добавить настройки размеров/шага и i18n-строки; проверить `getPlacementOptions`.
4. Реализовать `FatePointSync` для GM-ряда и его scene registry.
5. Обобщить placement и drag для групп без `actorUuid`.
6. Подключить синхронизацию actor-widget FP через публичный API `WidgetSync`.
7. Реализовать действия менеджера игроков и мастера с защитой от отрицательных
   значений и повторных операций.
8. Реализовать «Новую сцену» и очистку быстротечного стресса.
9. Добавить scene control, уведомления и документацию README.
10. Провести ручную проверку в чистой сцене и на сцене с уже размещёнными
    виджетами; затем отдельно проверить изменение layout/settings после
    размещения.

### 10. Критерии готовности

- Изменение FP игрока меняет число тайлов в его существующем widget без создания
  дубликатов и без смещения widget.
- Изменение FP мастера меняет отдельный GM-ряд на активной сцене; после reload и
  перетаскивания anchor сохраняется.
- При отсутствии изображения не остаются пустые Tile-документы.
- Все размещённые виджеты одного актёра синхронизируются одновременно.
- Значения FP не становятся отрицательными; refresh не уменьшает завышенный
  текущий запас.
- «Новая сцена» корректно обрабатывает отмену, перенос выбранных аспектов,
  очистку только быстротечного стресса и установку FP мастера.
- Изменение настроек размера/шага/изображения обновляет уже существующие ряды
  без изменения их anchor.
- Старые standalone-тайлы макроса не удаляются автоматически и не начинают
  управляться модулем без явной процедуры миграции.
- Проверено в Foundry v14 (минимум `14.354`) с `fate-core-official` и при
  включённом Advanced Drawing Tools.

## Зафиксированные решения

- **Представление на сцене**: набор отдельных `Drawing` + `Tile` (по документу на элемент), а не одна цельная сущность. Это даёт нативное редактирование элементов и дешёвое автообновление (правим только текст нужного drawing'а, без пере-растеризации).
- **Раскладка**: темплейт в `layouts.js`, координаты относительно якоря (верхний левый угол портрета), равномерный сдвиг `drawingOffset` для всех элементов кроме портрета.
- **Интерактив**: размещение + автосинк + перетаскивание группы. Кликабельность элементов (стресс-боксы и т.п.) — возможна отдельным этапом.
- **Шрифты**: только зарегистрированные в `CONFIG.fontDefinitions` (фолбэк на Montserrat с предупреждением). Не бандлим.

## Ключевые технические решения

### Идентификация группы (флаги)

- На каждом документе: `flags["chars-to-table"] = { widgetId, part, index, actorUuid }`.
- На актёре (регистр): `actor.setFlag("chars-to-table", "widgets", [{ widgetId, sceneId, anchor }])`.
- Осиротевшие записи (все документы удалены) чистятся при синке/размещении.

### Формат темплейта

```js
{
  id: "default",
  scale: 1,
  drawingOffset: { x: -135, y: -150 },          // сдвиг всех элементов кроме портрета
  bounds: { stroke: 1, alpha: 0.2, ... },       // «хватательный» бокс
  elements: [
    { id: "portrait", type: "tile", content: "@portrait", x: 0, y: 0, w: 270, h: 270 },
    { id: "name", type: "drawing", content: "@name", ..., matchBoundsWidth: true },
    { id: "skillName", type: "drawing", rows: "@skillNames", ..., stroke: 2, lineHeight: 68 },
    { id: "fatePointTokens", type: "tileRow", content: "@fatePointTokens", ..., step: 20 },
  ]
}
```

- Типы элементов: `tile`, `tileRow`, `drawing` (одиночный или `rows` — по документу на строку).
- `stroke` — обводка бокса; `weight` — fontWeight (ADT); `matchBoundsWidth` — растянуть на всю ширину листа.
- Резолверы `@name`, `@portrait`, `@aspects`, `@skillNames`, `@skillValues`, `@fatePointTokens`, заголовки через i18n.

### Размещение (PlacementManager)

- DOM-события `pointermove`/`pointerdown` на `canvas.app.view` (PIXI-события Foundry может перехватывать).
- Координаты: `clientX/Y` → масштаб канваса → `stage.worldTransform.applyInverse` (fallback: `event.getLocalPosition(canvas.controls)`).
- Коммит: батч-создание Drawing+Tile с флагами; превью — прямоугольник по реальным границам виджета.

### Автосинк (WidgetSync)

- `updateActor` + дебаунс 400мс; реконсиляция всех виджетов сцены по `canvasReady`.
- Диф по flat dotted-ключам (флаги обновляются безопасно, не затирая `chars-to-table`).
- Создание/удаление документов при изменении числа строк навыков/жетонов.

### ADT

- Все текстовые drawing'и получают `flags["advanced-drawing-tools"].textStyle = { dropShadow: false, strokeThickness: 0, align, fontWeight? }` и `flags.adt`.
