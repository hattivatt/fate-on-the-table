# План разработки модуля `fate-on-the-table`

Модуль Foundry VTT для Fate Core Official, который переносит данные персонажей
и игровые служебные элементы на канвас сцены в виде управляемых групп
`Drawing` + `Tile`. Группы можно размещать мышью, перетаскивать целиком и
автоматически синхронизировать с источниками данных системы.

Система: **только `fate-core-official`**. Foundry: **v14** (минимум `14.354`).

## Роадмап

1. **Альтернативные лейауты**:
   - загрузка и валидация раскладок из JSON;
   - перенос текущего `default` на новый формат;
   - встроенные `Default`, `Minimal`, `Full`;
   - отдельный выбор лейаута для персонажей игроков и NPC;
   - импорт/экспорт пользовательских JSON-раскладок внутри модуля;
   - отдельное standalone-приложение `../layout-editor` для визуального
     создания и редактирования JSON-раскладок.
2. **Розыгрыш конфликта на столе** — отдельный scene-widget с порядком ходов,
   отметками текущего/завершивших ход участников и интерактивным полем зон для
   токенов. Детальный первоначальный план ниже.
3. **Доработка виджета аспектов ситуации и зон в конфликте, а также
   взаимодействия между ними**.

Общие настройки, FP-менеджер и ситуативные аспекты уже реализованы и не должны
возвращаться в активный роадмап как новые фичи.

Перенос оставшихся legacy-макросов в модуль не планируется. Они остаются
отдельными макросами, если их использование понадобится в конкретной игре.

## Детальный план фичи 4 — альтернативные лейауты

Статус: **module-side реализован (этапы 0–8, 10); standalone-editor и

Граница ответственности:

- модуль умеет валидировать, загружать, хранить, выбирать и экспортировать
  раскладки;
- визуальное создание и изменение раскладки полностью вынесено в отдельный

- модуль не содержит `LayoutEditor.js`, canvas-конструктора или UI для

- подробный план standalone-приложения находится в

### 1. Исследование реализуемости

#### JSON-формат и загрузчик: высокая реализуемость

`LAYOUT-FORMAT.md` уже описывает версию JSON, virtual canvas, anchor,
элементы, resolver'ы, повторяющиеся строки/тайлы, относительные связи,
background и bounds.

Рекомендуемый путь:

1. Нормализовать JSON в текущую внутреннюю модель `WidgetBuilder`.
2. Не позволять JSON содержать JavaScript-код: только имена разрешённых
   resolver'ов и декларативные параметры.
3. Добавить schema validation и миграцию версий формата.
4. Оставить текущий builder источником фактических Drawing/Tile payloads.
5. После стабилизации заменить статический объект `layouts.js` реестром,
   который умеет загружать built-in JSON и custom JSON.

Загрузка JSON должна быть проверена в Foundry v14 отдельно. Варианты —
предварительная загрузка через `fetch` до регистрации настроек или импорт
пакетных файлов через поддерживаемый module asset pipeline. Нельзя полагаться
на неподтверждённую поддержку `import ... from "*.json"` без import assertion.

#### Визуальный редактор: реализуемость высокая, но вне модуля

Редактор будет отдельным статическим web-приложением в `../layout-editor`, а не
частью Foundry-модуля. Это убирает из модуля зависимости от editor UI, браузерных
File API, временных preview-объектов и сложной интерактивной геометрии.

Рекомендуемый стек и архитектура описаны в `../layout-editor/plan.md`:

- Vite + TypeScript + React;
- SVG virtual canvas с DOM inspector;
- palette, preview, selection, drag/resize и undo/redo;
- локальные JSON import/export без backend;
- тот же versioned layout contract, что использует модуль.

Foundry нужен только для runtime-части: загрузить JSON, проверить его и
преобразовать через `WidgetBuilder` в Drawing/Tile. Standalone-editor не должен
зависеть от `game`, `canvas`, Foundry permissions или серверного API.

#### Встроенные лейауты: высокая реализуемость

После появления loader'а три встроенные раскладки — это обычные JSON-ресурсы:

- `default.json` — перенос текущего `layouts.js` без изменения внешнего вида;
- `minimal.json` — имя, портрет и аспекты;
- `full.json` — все поддерживаемые блоки данных персонажа.

Редактор может использовать эти файлы как read-only templates и создавать от
них пользовательские копии. Поэтому наличие конструктора не является
предусловием для встроенных раскладок.

#### Разделение PC/NPC: высокая реализуемость

У Fate Core Actor есть `actor.hasPlayerOwner`, а исходный system code уже
использует это свойство. Для надёжности нужен fallback на проверку
`testUserPermission` для всех не-GM пользователей.

В настройках можно зарегистрировать два выбора:

- `playerLayout` — лейаут актёров с игроками-владельцами;
- `npcLayout` — лейаут актёров без игроков-владельцев.

Внутри layout selection не следует дублировать раскладки: обе настройки хранят
только `layoutId` и используют общий реестр.

### 2. Единая модель layout registry

Добавить слой между JSON и текущими `layouts.js`:

- `layoutSchema.js` — проверка версии, обязательных полей и ссылок между
  элементами;
- `layoutRegistry.js` — built-in, custom и публичная регистрация раскладок;
- `layoutLoader.js` — загрузка JSON-ресурсов, импорт и нормализация;
- `layouts/*.json` — встроенные раскладки.

Каждая зарегистрированная раскладка получает:

```js
{
  id,
  name,
  source: "builtin" | "custom" | "registered",
  version,
  document
}
```

Custom layouts хранить в world setting как массив JSON-документов. Built-in
раскладки нельзя изменять напрямую: редактор создаёт custom copy с новым id.
Публичный API должен позволять другим модулям зарегистрировать layout в памяти
до построения списка выбора.

### 3. Миграция текущей раскладки

Первым реальным кодовым шагом сделать loader только для текущего `default`:

1. Перенести эффективную геометрию и правила из `layouts.js` в
   `layouts/default.json` по `LAYOUT-FORMAT.md`.
2. Сохранить текущие resolver'ы `@name`, `@portrait`, `@aspects`,
   `@skillNames`, `@skillValues`, `@fatePointTokens` и заголовки.
3. Сравнить output нового loader и старого builder по каждому типу документа:
   `kind`, `part`, `index`, координаты, размеры, текст, style и flags.
4. Только после совпадения переключить `getLayout("default")` на registry.

В actor registry текущих виджетов сейчас нет `layoutId`: там хранятся widget id,
scene id и anchor. При миграции:

- старую запись считать layout `default` или текущим legacy fallback;
- при первом успешном sync дописать `layoutId` и `layoutVersion`;
- не терять anchor и не создавать новый widget;
- не менять layout старого виджета неожиданно только из-за загрузки JSON.

Новые записи должны хранить layout identity:

```js
{
  widgetId,
  sceneId,
  anchor: { x, y },
  layoutId: "default",
  layoutVersion: 1
}
```

Это позволит существующему виджету оставаться на выбранной раскладке, даже если
дефолт для новых размещений позже изменён.

### 4. Каталог элементов персонажа

Конструктор не должен разрешать произвольные resolver strings без проверки.
Нужен каталог семантических элементов с типом данных и правилами preview.

#### Базовые элементы

- `name` — имя актёра;
- `portrait` — портрет актёра;
- `aspects` — аспекты актёра;
- `skills` — навыки с группировкой по рангу;
- `fatePoints` — текущие FP и/или ряд жетонов;
- `stressTracks` — треки стресса и их боксы;
- `consequences` — занятые и свободные последствия.

#### Расширенные элементы

- `stunts` — название, описание, связанный навык, бонус;
- `extras` — embedded Items типа `Extra`;
- `biography`, `description`, `notes` — rich-text поля актёра;
- `boosts`, `refresh`, `pronouns` и другие простые поля details;
- `track` — отдельный выбранный трек с настройкой отображения.

Источники данных Fate Core подтверждены локальным `FateCoreOfficialModels.js`:

- `system.aspects`, `system.skills`, `system.stunts`, `system.tracks` —
  объектные коллекции;
- `system.details.fatePoints` — current/refresh/boosts;
- `system.details.description`, `biography`, `notes` — HTML/string fields;
- `actor.items` содержит Extras.

Нужно не зашивать в layout конкретные имена вроде «Physical Stress». Треки
должны классифицироваться по данным (`recovery_type`, `aspect`, `enabled`,
`category`) и поддерживать пользовательские/системные дополнительные треки.
Последствия — это отдельный представляемый вид треков, обычно `Lasting` с
`track.aspect`, а не отдельная коллекция в actor data.

Rich-text поля перед выводом на Drawing должны проходить отдельный formatter:
либо безопасное обогащение с потерей HTML, либо явное text-only представление.
JSON раскладки не должен содержать HTML/JavaScript, если это не разрешено
конкретным renderer'ом.

### 5. Три встроенные раскладки

#### `Default`

Точный перенос текущей раскладки:

- имя над портретом;
- портрет слева;
- аспекты справа;
- FP-жетоны под портретом;
- таблица навыков;
- текущий фон и drag-box.

#### `Minimal`

Содержит только:

- имя;
- портрет;
- аспекты.

Минимальный layout всё равно должен иметь background/bounds и корректные
динамические bounds. Отсутствие навыков/треков/жетонов означает отсутствие
соответствующих документов, а не пустые Drawing.

#### `Full`

Содержит все поддержанные на первом этапе каталога данные:

- имя и портрет;
- Fate Points/refresh;
- аспекты;
- навыки;
- стрессовые треки и боксы;
- последствия;
- трюки;
- Extras;
- при необходимости описание/биографию.

Полный layout следует сделать читабельным, а не просто сложить все элементы в
один длинный список. Для него заранее выбрать orientation и несколько секций с
явными bounds. Если данных нет, секция скрывается или получает пустое состояние
по декларативному правилу layout.

### 6. Разделение раскладок для PC и NPC

Добавить настройки:

- `playerLayout` — layout для Actor с хотя бы одним non-GM OWNER;
- `npcLayout` — layout для Actor без player owner.

Правила выбора:

1. Для placement определить `actor.hasPlayerOwner`.
2. Если свойство недоступно или не определено, проверить
   `actor.testUserPermission(user, OWNER)` по всем non-GM users.
3. Получить layout id из соответствующей настройки.
4. Если выбранный id удалён/невалиден, использовать `default` и показать
   предупреждение GM.
5. Явный layout id, сохранённый в widget registry, имеет приоритет над текущим
   default selection для уже размещённого widget.

В будущем можно добавить выбор layout непосредственно в placement dialog, но
первый этап должен работать только через две настройки, как требуется сейчас.

### 7. Граница с standalone layout-editor

В модуле не будет интерактивного конструктора, preview-редактора или
`LayoutEditor.js`. Эти функции реализуются в отдельном приложении;
архитектура, UI и этапы находятся в `../layout-editor/plan.md`.

Модуль обязан поддерживать только контракт обмена:

- экспортировать валидный JSON built-in/custom layout;
- импортировать JSON, созданный standalone-editor;
- валидировать и нормализовать JSON до записи;
- показывать список элементов и ошибки импорта;
- использовать импортированный layout в `WidgetBuilder` без ручной конвертации.

#### Сохранение и импорт/экспорт

Импорт/экспорт в модуле нужен для того, чтобы standalone-editor мог обмениваться
раскладками с Foundry:

- built-in layout открывается read-only;
- module UI импортирует JSON из выбранного файла или текстового буфера;
- импорт валидирует `format`, `version`, resolver'ы и ссылки между элементами;
- валидная раскладка сохраняется как custom layout в world setting
  `customLayouts` после подтверждения;
- export выбранной custom/built-in раскладки создаёт JSON-файл через
  Blob/download;
- при неизвестном resolver импорт блокируется с указанием элемента и поля;
- custom layout нельзя частично сохранить при ошибке validation;
- миграции schema version выполняются до записи в registry.

Визуальное «Сохранить как», drag/resize и редактирование draft выполняются
только в `../layout-editor`, а не в этом UI модуля.

### 8. Публичный API реестра

После появления loader'а предоставить минимальный API:

- `registerLayout(layout)`;
- `getLayout(id)`;
- `getLayoutIds()`;
- `validateLayout(layout)`;
- `exportLayout(id)` или получение нормализованного JSON-документа.

Регистрация должна происходить после загрузки встроенных JSON и до отображения
списков настроек. Внешний модуль может добавить layout, но не может заменить
зарегистрированный built-in id без явного override policy.

### 9. Порядок реализации

Реализация разбивается на последовательные этапы. Переходить к следующему
этапу можно после выполнения его exit criteria; полноценный редактор не должен
блокировать загрузчик и встроенные раскладки.

#### Этап 0 — зафиксировать контракт и fixtures

- [x] Принять `LAYOUT-FORMAT.md` как schema v1 и выписать обязательные поля,
  допустимые значения enum и правила ссылок между элементами.
- [x] Сохранить JSON-fixture текущего `default` и несколько маленьких fixtures:
  статический текст, tile, rows, tileRow, frame/growTo, background и bounds.
- [x] Описать fixture Actor с пустыми skills/tracks/stunts и fixture с
  максимальным набором данных.
- [x] Зафиксировать, что editor и loader работают только с разрешёнными
  resolver'ами, а не с произвольным кодом.

**Результат:** схема и тестовые данные, не зависящие от Foundry canvas.

#### Этап 1 — чистый validator и normalizer

## Детальный первоначальный план фичи 5 — «Розыгрыш конфликта на столе»

Статус: **не начата**.

Цель — дать GM отдельное поле конфликта на активной сцене, где видны зоны,
участники, порядок ходов и состояние текущего раунда. Нативные Token-документы
остаются источником их положения, vision, ownership и стандартного взаимодействия;
конфликтный board хранит только состояние конфликта и проекцию зон.

### Состав фичи

- порядок участников конфликта;
- текущий участник и номер раунда;
- отметки «ход ещё не начат», «ходит сейчас», «ход завершён»;
- переход к следующему/предыдущему участнику;
- завершение хода и сброс отметок на новый раунд;
- создание, переименование, перемещение, изменение размера и удаление зон;
- перемещение токенов между зонами;
- сохранение состояния на сцене и восстановление после reload;
- GM-интерфейс управления и видимый для игроков board.

### Источник истины

Стандартный конфликт уже существует в Foundry как `game.combat`. Текущий
`fate-core-official` использует его `combatants`, `turn`, `round` и флаг
`fate-core-official.hasActed` у `Combatant`. Не создавать второй независимый
порядок ходов в module flag.

Источники состояния:

- очерёдность участников — `game.combat.combatants` в текущем порядке;
- текущий ход — `game.combat.turn`;
- номер раунда — `game.combat.round`;
- отметка «походил» — `combatant.getFlag("fate-core-official", "hasActed")`;
- token/actor — `combatant.token` и `combatant.token.actor`;
- геометрия board, зоны и раскладка карточек — scene flag модуля.

Module flag имеет вид:

```js
scene.flags["fate-on-the-table"].conflictBoard = {
  version: 1,
  combatId: "<combatId>",
  sizePreset: "medium",
  board: {
    origin: { x: 1000, y: 800 },
    background: { color: "#ffffff", texture: "" }
  },
  zones: [
    {
      id: "zone-1",
      name: "Центр комнаты",
      rect: { x: 1200, y: 1000, width: 400, height: 300 },
      style: { fill: "#ffffff", alpha: 0.12, stroke: "#000000" },
      sort: 0
    }
  ],
  cards: {
    "<combatantId>": {
      side: "friendly",
      area: "side",
      order: 0
    }
  },
  tokenZones: {
    "Scene.<sceneId>.Token.<tokenId>": "zone-1"
  }
};
```

Правила:

- `combatId` связывает board с конкретным конфликтом Foundry;
- Token UUID и Combatant id, а не имя токена, являются идентификаторами карточек;
- удалённый или недоступный combatant удаляется из card assignments при reconcile;
- current/acted состояние вычисляется из `game.combat.turn` и
  `fate-core-official.hasActed`, а не дублируется в board flag;
- zone ids стабильны и не зависят от порядка массива;
- фактические `TokenDocument.x/y` остаются каноническими координатами токена;
- `tokenZones` хранит принадлежность к зоне, а не дублирует полную позицию;
- чужие Drawing/Token-документы не определяются и не удаляются по координатам
  или тексту.

### Кнопки размещения

Кнопка «Разместить конфликт на столе» должна появляться только когда есть
активный конфликт с combatants, чьи токены доступны на текущей сцене.

Добавить её в два места:

1. стандартный интерфейс Foundry в области текущего конфликта;
2. вкладка конфликтов в `Fate Utilities`, через уже используемый в модуле
   `renderFateUtilities` hook.

Оба входа должны вызывать одну функцию `ConflictManager.placeBoard()` и не
создавать разные варианты board. Если текущий конфликт не привязан к активной
сцене, кнопку скрывать или показывать с понятным предупреждением.

### Геометрия board

При нажатии кнопки перед placement показать ApplicationV2/DialogV2 с тремя
вариантами размера:

- `small` — небольшой квадрат;
- `medium` — средний квадрат;
- `large` — большой квадрат.

Конкретные размеры зафиксировать в одном конфиге, например `small/medium/large`
в scene units. В state сохранять и preset, и рассчитанный `boardSize`, чтобы
изменение defaults в будущем не меняло существующие board.

Board состоит из пяти областей:

```text
┌────────────┬──────────────────────┬────────────┐
│ friendly   │                      │ hostile    │
│ cards      │   квадрат поля       │ cards      │
│            │                      │            │
├────────────┴──────────┬───────────┴────────────┤
│       Походил         │          Выбыл          │
│   pile minimal cards  │     pile minimal cards  │
└───────────────────────┴────────────────────────┘
```

- центральное поле — квадрат `boardSize × boardSize`;
- боковые области имеют высоту поля и ширину не меньше ширины minimal
  персонажного widget плюс padding;
- нижние области имеют высоту не меньше minimal widget и ширину, достаточную
  для одной карточки; карточки в них могут перекрываться стопкой;
- фактические bounds board включают все пять областей и внутренние отступы;
- placement preview показывает весь board, а не только центральный квадрат.

При placement карточка выбирается из `minimal` layout, но её anchor/rect
преобразуются в координаты соответствующей области board.

### Фон board

В штатных настройках модуля добавить отдельные настройки конфликта:

- цвет фона board, default `#ffffff`;
- texture path, пустое значение означает цветовую заливку;
- при необходимости alpha.

Эти настройки не используют `backgroundTexture` actor-widget или фон
situation-aspects. При размещении background создаётся отдельным module-owned
Drawing/Tile под квадратом и областями карточек. Изменение настройки обновляет
уже размещённый board без изменения его origin.

### Представление на сцене

Зоны являются module-owned scene-widget группами:

- отдельный Drawing-элемент зоны с fill/stroke;
- отдельный Drawing с названием зоны;
- общий `widgetId`/`ownerType: "conflictZone"`;
- registry board хранит список zone widget ids или общий board widget id;
- слой зон должен находиться под токенами и не блокировать обычный token drag,
  когда режим редактирования поля выключен.

В режиме редактирования GM получает overlay/handles для зон. Вне режима зоны
видимы как обычная часть board, но не перехватывают управление токенами.

### Карточки участников

При первом размещении board взять участников из `game.combat.combatants`, а не
из всех токенов сцены. Участник подходит для карточки, если у него есть
доступный Token на текущей сцене.

Для каждой карточки:

- использовать minimal layout;
- имя брать из `combatant.token.name`/`TokenDocument.name`, а не из Actor;
- портрет брать из `combatant.token.texture.src`, а не из Actor image;
- остальные поля minimal widget получать из `combatant.token.actor`;
- сохранять связь с `combatant.id` и `token.uuid`;
- при изменении имени или texture токена обновлять карточку;
- при удалении combatant удалять карточку из соответствующей области.

Распределение по сторонам при первичном размещении:

- PC с player owner — в левую область;
- Token с `CONST.TOKEN_DISPOSITIONS.FRIENDLY` — в левую область;
- Token с `CONST.TOKEN_DISPOSITIONS.HOSTILE` — в правую область;
- `NEUTRAL` и неизвестные значения — временно в левую область с возможностью
  ручного переноса в будущем.

В боковой области карточки складываются вертикально с фиксированным gap. Если
карточек больше доступной высоты, board не должен молча обрезать их: нужно либо
расширить боковую область по настройке, либо показывать понятный overflow.

Карточки участника должны быть отдельными actor-widget-группами с флагами:

```js
flags["fate-on-the-table"] = {
  widgetId,
  ownerType: "conflictCard",
  combatId,
  combatantId,
  tokenUuid,
  area: "friendly" | "hostile" | "acted" | "eliminated"
};
```

Позиция карточки вычисляется из board state и области. Ручное перемещение
карточки не должно менять `TokenDocument.x/y`: карточка перемещается между
областями board, а не становится вторым токеном.

### Интерактив карточек и board

Двойной клик по карточке открывает чарник привязанного токена/синтетического
Actor. Использовать Token/Combatant UUID, чтобы открыть именно тот объект,
который участвует в текущем конфликте, включая unlinked token actor.

Правый клик по карточке открывает контекстное меню:

- единственная первая операция — **«Передать ход»**;
- операция доступна только GM и только для участника, который не является
  текущим и ещё не имеет `hasActed`;
- при выборе текущий Combatant получает `hasActed: true`, его карточка
  перемещается в нижнюю область «Походил», а `game.combat.turn` переключается
  на выбранного Combatant;
- выбранная карточка остаётся в своей боковой области и получает marker
  текущего хода;
- если текущего хода ещё нет, первый выбранный участник становится текущим,
  а предыдущая карточка не перемещается.

Правый клик по центральному квадрату board открывает контекстное меню:

- **«Добавить зону»**;
- **«Следующий раунд»**.

Для «Добавить зону» запросить название, затем запустить drag-preview
прямоугольника только внутри центрального квадрата. После подтверждения создать
zone Drawing поверх board. На первой версии у зоны нет собственных действий.

«Следующий раунд» доступен только когда в текущем раунде нет Combatant, которому
ещё можно передать ход. При выполнении:

- сбросить `hasActed` у combatants текущего конфликта;
- увеличить `game.combat.round` через штатный API;
- установить `game.combat.turn` в `null`, чтобы новый ход можно было выбрать
  вручную;
- вернуть карточки из «Походил» в исходные friendly/hostile области;
- снять marker текущего хода;
- сохранить board state, не удаляя зоны и token membership.

Если текущий участник ещё не отмечен как походивший, «Следующий раунд» должен
быть заблокирован, пока GM не передаст ход или явно не завершит его штатным
действием.

Карточка текущего участника получает отдельный marker Drawing поверх карточки.
На первой версии marker может быть простой рамкой, заливкой или небольшим
текстовым Drawing. Marker должен иметь собственный part и обновляться при
изменении `game.combat.turn`.

### Управление порядком ходов

Добавить GM-only инструмент «Конфликт» в scene controls и отдельное ApplicationV2
окно управления:

- добавить участников из токенов текущей сцены;
- удалить участника;
- изменить порядок drag-and-drop или кнопками вверх/вниз;
- выбрать начального участника;
- показать номер раунда;
- кнопки «Следующий ход», «Предыдущий ход», «Завершить ход», «Новый раунд»;
- визуально выделять current participant и завершивших ход;
- при удалении/перемещении токена обновлять board state без потери порядка.

Игрокам можно показывать read-only порядок и текущий ход, но операции изменения
порядка и зон должны быть GM-only. Позже можно добавить ownership-based право
игрока завершать только собственный ход.

### Зоны и перемещение токенов

Реализация по этапам:

1. MVP: GM создаёт прямоугольную зону drag-ом на canvas и задаёт ей имя через
   небольшое ApplicationV2-окно.
2. Зону можно выбрать, переместить и изменить размер; изменения сохраняются в
   `conflictBoard.zones` и обновляют Drawing projection.
3. В контекстном меню зоны показать список токенов и команды перемещения.
4. В board mode разрешить перетаскивание токена в другую зону; при drop:
   - определить целевую зону;
   - обновить `tokenZones`;
   - поставить токен в свободную/выбранную snap-точку внутри зоны;
   - сохранить обычные `TokenDocument.x/y` через штатный API.
5. При ручном перемещении токена вне board mode пересчитать membership или
   очистить его, если токен покинул все зоны.
6. Перемещение одного токена не должно запускать изменение его Actor или
   actor-widget, кроме уже существующих стандартных hooks.

На первом этапе зоны — прямоугольники. Круги, полигоны, вложенные зоны,
автоматическая раскладка токенов и измерение дистанции оставить расширением.

### Будущие расширения

Следующие возможности не входят в первую версию, но должны быть предусмотрены
в schema v1/v2 и не требовать переделки базового board:

- действия зоны: переименование, изменение стиля, перемещение, resize и
  удаление с подтверждением;
- привязка зоны к одному или нескольким ситуативным аспектам;
- отображение названия аспекта, количества invoke и быстрый переход в
  менеджер ситуативных аспектов;
- зоны с препятствиями, дистанциями, стоимостью перемещения и ограничениями;
- ручное действие «Выбыл» для карточки с перемещением в нижнюю область
  `Выбыл` и опциональным удалением Combatant из текущего конфликта;
- автоматическое предложение переместить карточку в `Выбыл` при удалении
  Combatant или его Token;
- дополнительные действия карточки: вернуть в бой, временно скрыть,
  отметить NPC/PC, открыть связанные аспекты;
- круговые/полигональные зоны и вложенные зоны;
- автоматическая раскладка карточек внутри области и раскрытие pile;
- marker текущего хода в виде иконки, подсветки или рамки из настройки;
- связь board с `game.combat` lifecycle и переключением между несколькими
  конфликтами.

Завершение конфликта должно быть отдельной явной операцией, доступной из
стандартного conflict UI и Fate Utilities. Перед завершением показать диалог с
опциональными действиями:

- завершить/деактивировать текущий `game.combat`;
- оставить board и зоны на сцене как историческую запись;
- удалить board, зоны и карточки;
- вернуть карточки из `Походил`/`Выбыл` в обычное состояние или удалить их;
- сбросить `hasActed`;
- очистить быстротечный стресс;
- сохранить snapshot конфликта в scene flag или экспортировать его.

Никакая очистка не должна выполняться автоматически только из-за закрытия
combat UI или переключения на другой конфликт.

### Взаимодействие с текущей архитектурой

Планируемые новые модули:

- `ConflictManager.js` — ApplicationV2 управления конфликтом и turn order;
- `ConflictBoardSync.js` — нормализация scene state и reconcile;
- `ConflictZoneEditor.js` — canvas overlay для создания/resize/move зон;
- `ConflictInteractions.js` — token-to-zone drag/drop и click routing.

Переиспользовать:

- scene-owned registry/flags из FP и situation aspects;
- `PlacementManager` для первоначального размещения board/зон;
- `widgetDrag` для группового движения zone projection;
- `canvas` coordinate conversion и DOM/PIXI overlay подход;
- ApplicationV2 и scene control conventions текущего модуля.

Не объединять конфликтный board с actor-widget: actor-widget отвечает за
карточку персонажа, board — за положение токенов и ход конфликта. Связь между
ними выполняется по Token UUID/Actor UUID.

### Порядок реализации

1. Ввести schema v1 и нормализатор `conflictBoard` без canvas-зависимости.
2. Сделать read-only board projection для уже сохранённого state.
3. Реализовать список участников и turn order без зон.
4. Добавить текущий ход, завершение хода, раунды и визуальные состояния.
5. Добавить CRUD прямоугольных зон и их scene Drawing projection.
6. Добавить режим редактирования зон с preview/handles и сохранением.
7. Добавить token membership и перемещение токенов между зонами.
8. Подключить `canvasReady`, `updateScene`, `updateToken`, удаление токенов и
   reconcile осиротевших участников/зон.
9. Добавить GM/player permissions, i18n, README и ручной чек-лист.
10. После стабилизации оценить дополнительные формы зон и интеграцию с
    `game.combat`; собственный board state остаётся базовым источником истины.

### Критерии готовности первой версии

- GM может создать board на сцене и добавить токены из текущей сцены.
- Кнопка размещения появляется и в стандартном conflict UI Foundry, и в
  соответствующей вкладке Fate Utilities, при наличии текущего конфликта.
- Перед размещением GM выбирает `small`, `medium` или `large`; центральное поле
  остаётся квадратным.
- Слева/справа есть области высотой поля для minimal-карточек, а снизу —
  области «Походил» и «Выбыл» с поддержкой pile.
- Цвет/текстура board настраиваются отдельно от фонов других виджетов.
- Первичное распределение карточек использует combatants, disposition,
  player ownership, имя токена и texture токена.
- Участники имеют стабильный порядок, один текущий участник и понятные отметки
  завершённого хода.
- «Следующий ход» корректно переходит к следующему участнику и начинает новый
  раунд после последнего.
- Двойной клик по карточке открывает связанный чарник; правый клик предлагает
  «Передать ход» только для допустимого участника.
- Правый клик по центральному полю предлагает «Добавить зону» и
  «Следующий раунд» с указанными ограничениями доступа.
- Текущий участник отмечен отдельным Drawing marker; при передаче хода прежняя
  карточка попадает в «Походил».
- GM может создать, назвать, переместить, изменить размер и удалить зону.
- Токен можно перевести в другую зону, а после reload принадлежность сохраняется.
- Нативное движение токенов, vision, ownership и standard Token HUD не ломаются.
- Игроки видят board, но не могут менять порядок/зоны без отдельного разрешения.
- Осиротевшие Token UUID и удалённые зоны безопасно очищаются.
- Состояние конфликта не зависит от legacy-макросов.

## Зафиксированные решения

- **Представление на сцене**: группы состоят из отдельных `Drawing` + `Tile`, а
  не из одной растеризованной картинки. Это даёт нативное редактирование и
  дешёвый автосинк.
- **Actor-widget**: actor-owned документы используют `actorUuid` и реестр
  `actor.flags["fate-on-the-table"].widgets`.
- **Scene-widget**: GM FP и ситуативные аспекты используют `ownerType`, scene
  registry и не требуют `actorUuid`.
- **Источники данных**: FP игрока хранится в actor system data, FP мастера — в
  совместимом системном user flag, ситуативные аспекты — в системном scene
  flag `fate-core-official.situation_aspects`.
- **Раскладки**: после фичи 4 источником layout data является versioned JSON,
  а builder работает с нормализованной внутренней моделью.
- **Редактор раскладок**: draft редактируется в отдельном standalone web-app и
  не создаёт временные Drawing/Tile-документы на сцене. Модуль содержит только
  runtime loader и import/export.
- **Интерактив сцены**: placement, автосинк и групповой drag входят в базовую
  инфраструктуру; кликабельные игровые элементы добавляются отдельными
  фичами.
- **Настройки**: новые функции используют штатные `game.settings`, а не
  JSON-страницы журнала старого набора макросов.
- **Шрифты**: используются только зарегистрированные в
  `CONFIG.fontDefinitions`; незарегистрированный шрифт заменяется на
  Montserrat с предупреждением.
- **Legacy-объекты**: старые документы макросов не удаляются автоматически без
  явной процедуры миграции.

## Ключевые технические решения

### Идентификация групп

- Actor-widget:
  `flags["fate-on-the-table"] = { widgetId, part, index, actorUuid }`.
- GM scene-widget:
  `flags["fate-on-the-table"] = { widgetId, part, index, ownerType: "gm" }`.
- Situation aspect scene-widget:
  `flags["fate-on-the-table"] = { widgetId, part, index, ownerType: "situationAspects" }`.
- Осиротевшие записи очищаются только по module flags и registry; поиск по
  содержимому текста Drawing не используется.

### Формат layout

JSON layout содержит version, id, anchor, virtual canvas, background, bounds и
массив элементов. Каждый элемент имеет type, rect, content/resolver, style и
опциональные repeat/position/sizing правила. Внутри runtime:

```text
JSON -> validate/normalize (layoutSchema) -> resolve data (resolver catalog)
     -> geometry (layoutGeometry) -> WidgetBuilder -> Drawing/Tile
```

Resolver catalog является единственным местом, где разрешается код подготовки
данных. Сам JSON остаётся декларативным. Чистые модули (`layoutSchema`,
`layoutGeometry`, `layoutRegistry`) не зависят от Foundry и покрыты Node-тестами
в `tests/` (`npm test`). Геометрия `default` проверяется на паритет с прежней
`layouts.js` (включая legacy-конвертацию `legacyToJson` как fallback при
недоступности JSON-ресурсов).

Widget records хранят layout identity:

```js
{ widgetId, sceneId, anchor: { x, y }, layoutId: "default", layoutVersion: 1 }
```

Legacy-записи без identity получают роль-раскладку (`playerLayout`/`npcLayout`)
при первом успешном синке; явная смена раскладки через меню чарника имеет
приоритет над настройками.

### Placement и автосинк

- Placement использует DOM-события `pointermove`/`pointerdown` на
  `canvas.app.view`, потому что PIXI-события могут перехватываться Foundry.
- Координаты получают через inverse world transform или публичные методы Canvas
  преобразования координат.
- Коммит создаёт документы batch-запросами и сохраняет registry после успешного
  создания.
- `updateActor` вызывает actor-widget sync с debounce 400 мс.
- `canvasReady` выполняет реконсиляцию actor-widget и синхронизацию scene-owned
  групп.
- Обновления, инициированные синком, помечаются `fateOnTheTableSync`, чтобы не
  запускать рекурсивный групповой drag.

### Advanced Drawing Tools

Текстовые Drawing получают ADT-флаги с `dropShadow: false`,
`strokeThickness: 0`, `align` и при необходимости `fontWeight`.
