# План разработки модуля `chars-to-table`

Модуль Foundry VTT для Fate Core Official, который переносит данные персонажей
и игровые служебные элементы на канвас сцены в виде управляемых групп
`Drawing` + `Tile`. Группы можно размещать мышью, перетаскивать целиком и
автоматически синхронизировать с источниками данных системы.

Система: **только `fate-core-official`**. Foundry: **v14** (минимум `14.354`).

## Детальный план следующей фичи — «Менеджер ситуативных аспектов»

Статус: **реализована** (см. «Статус — Фича 3» выше; раздел оставлен как
справочный рекорд решений).

Цель — перенести управление ситуативными аспектами из
`foundry_macro/sit_aspects.js`, сохранив системный формат данных Fate Core и
переведя виджет на общую инфраструктуру модуля: scene registry, placement,
групповой drag, флаги документа и синхронизацию.

### 1. Объём и границы фичи

В первую реализацию входят:

- GM-диалог со списком аспектов;
- добавление, переименование и удаление аспектов;
- увеличение и уменьшение `free_invokes` с нижней границей ноль;
- сохранение в системный scene flag;
- виджет списка на активной сцене;
- ручное размещение, переразмещение, удаление и групповое перемещение виджета;
- отдельный настраиваемый фон виджета, независимый от фона виджета персонажа и
  ряда FP мастера;
- обновление виджета при изменении флага, настроек и операции «Новая сцена»;
- штатные настройки размера, шрифта и цвета.

Не входят в эту фичу:

- интерактивное списывание invoke кликом по конкретному аспекту на сцене;
- привязка аспекта к токену/актёру отдельным полем данных: принадлежность
  обозначается текстово `Аспект (Персонаж)` (реализовано — см. статус
  фичи 3);
- изменение системной модели аспектов;
- автоматическое удаление или преобразование старых Drawing из макроса.

### 2. Источник истины и формат данных

Использовать уже существующий системный флаг:

```js
scene.getFlag("fate-core-official", "situation_aspects")
```

Значение — массив объектов минимум такого вида:

```js
[
  { name: "В огне", free_invokes: 2 },
  { name: "Плохая видимость", free_invokes: 0 }
]
```

Правила работы с данными:

1. При чтении глубоко клонировать массив, чтобы не мутировать данные сцены до
   подтверждения пользователем.
2. Преобразовывать `free_invokes` в целое неотрицательное число. Это исправляет
   старую проблему со строковым сложением из `sit_aspects.js`.
3. Обрезать имя после `trim()` и не разрешать пустые имена.
4. Не использовать имя аспекта для поиска Drawing: переименование и удаление
   должны работать только с draft-массивом и системным флагом.
5. Не добавлять обязательный id к объектам, пока это не требуется системой:
   операции внутри редактора работают по индексу draft-массива, а виджет
   хранит весь список одним текстовым Drawing.
6. Не менять неизвестные дополнительные поля объектов аспектов при сохранении,
   если они уже присутствуют в системном флаге.

### 3. Идентификация виджета на сцене

Виджет должен использовать собственный scope модуля, а не legacy-флаги `core`:

```js
flags["chars-to-table"] = {
  widgetId,
  part: "situationAspectsText",
  index: -1,
  ownerType: "situationAspects"
}
```

Реестр одной группы на сцене:

```js
scene.getFlag("chars-to-table", "situationAspectsWidget")
// { widgetId, anchor: { x, y } }
```

Если виджет состоит из фона, текста и прозрачного frame, все документы
используют одинаковый `widgetId` и `ownerType`. `actorUuid` у них отсутствует.

Фон получает отдельную часть, например `situationAspectsBackground`, и не
использует `backgroundTexture` actor-widget. Это позволяет менять внешний вид
виджета персонажа и виджета ситуативных аспектов независимо.

Legacy-объект из `sit_aspects.js` имеет флаг
`core.situationAspectsWidget`. Модуль не должен автоматически удалять его или
начинать менять по совпадению текста. При необходимости импорт/очистка старых
объектов будет отдельной миграционной операцией.

### 4. Структура кода

Предполагаемые новые файлы:

- `scripts/SituationAspectManager.js` — ApplicationV2-диалог, draft-редактор,
  команды сохранения, открытия и размещения.
- `scripts/SituationAspectSync.js` — нормализация данных, построение текста и
  frame, синхронизация документов, scene registry и очистка осиротевшей записи.

Изменения существующих файлов:

- `scripts/constants.js` — ключи системного флага, scene registry и
  `ownerType`.
- `scripts/settings.js` — настройки виджета и их runtime-значения.
- `scripts/module.js` — регистрация менеджера, хуков и scene control.
- `scripts/PlacementManager.js` — переиспользовать существующий
  `placeGroup` для группы без актёра.
- `scripts/widgetDrag.js` — обобщить обновление scene anchor для
  `ownerType: "situationAspects"`, не ломая ветки actor-widget и GM FP.
- `scripts/FatePointManager.js` — оставить `newScene` как источник изменения
  системного флага; новый менеджер должен подписаться на
  `chars-to-table.newScene` и обновлять существующий виджет.
- `languages/{en,ru}.json` и `styles/module.css` — UI, уведомления и стили.

Общие функции синхронизации и placement не дублировать в новом менеджере.

### 5. Диалог менеджера

Добавить GM-only инструмент «Менеджер ситуативных аспектов» в scene controls.
Если виджет уже размещён, двойной клик по его frame, фону или тексту должен
открывать это же меню. Для игроков двойной клик не должен открывать редактор.

Диалог работает с локальным draft и содержит:

- список аспектов: название и число свободных invoke;
- `+`/`−` для изменения invoke;
- кнопки переименования и удаления;
- «Добавить»;
- «Сохранить» или «Сохранить и закрыть»;
- «Разместить на столе» / «Переразместить»;
- «Отмена» без записи изменений.

Меню, открываемое двойным кликом, должно быть основным оперативным меню,
аналогичным меню виджета FP мастера и старому `sit_aspects.js`:

- список всех текущих аспектов ситуации;
- возле каждого аспекта — текущее число свободных invoke и кнопки `+`/`−`;
- действие добавления нового аспекта с названием и начальным числом invoke;
- действие удаления старого аспекта с подтверждением;
- действие переименования аспекта, как в исходном макросе;
- сохранение списка и обновление уже размещённого Drawing.

То есть двойной клик не должен открывать только настройки геометрии или
отдельное информационное окно: из открывшегося меню должны быть доступны все
операции управления аспектами, кроме действий, явно ограниченных GM.

Правила действий:

1. При открытии взять snapshot текущего scene flag и нормализовать его.
2. При добавлении открыть небольшую форму с названием и начальным числом
   invoke; по умолчанию использовать `1`, минимум `0`.
3. При переименовании предварительно заполнить старое имя и запретить пустое
   новое имя.
4. При удалении запрашивать подтверждение; удалять элемент draft по индексу.
5. Уменьшение invoke не должно давать значение ниже нуля.
6. Сохранение выполнить одним `scene.setFlag(...)`, затем вызвать синхронизацию
   виджета. Если виджет не размещён, флаг всё равно сохранить, но автоматически
   создавать Drawing не нужно.
7. После операции заново отрисовать значения из документов сцены, чтобы диалог
   не показывал устаревший draft.
8. Экранировать пользовательские строки в HTML диалога; текст Drawing передавать
   как обычный текст, не как HTML.
9. Пока выполняются update/create/delete, блокировать повторные клики и выводить
   ошибку одновременно в консоль и через `ui.notifications`.

### 6. Виджет и геометрия

Сохранить визуальное поведение исходного макроса: список формируется как
`name (free_invokes)`, элементы разделяются пустой строкой и выравниваются по
центру Drawing.

Виджет состоит из:

- `situationAspectsBackground` — Drawing-подложка под текстом и frame;
- `situationAspectsText` — Drawing с полным текстом списка;
- `situationAspectsFrame` — прозрачный «хватательный» Drawing, покрывающий
  область текста и позволяющий перемещать группу даже при пустом списке.

Параметры геометрии:

- anchor выбирается пользователем в placement-flow;
- ширина и высота берутся из настроек;
- текст и frame имеют один anchor и один `widgetId`;
- фон покрывает те же bounds, имеет низкие `elevation`/`sort` и не перехватывает
  двойной клик у текста или frame;
- при изменении длины текста frame не должен менять anchor;
- текущий viewport, pan и grid учитываются существующим
  `PlacementManager.placeGroup`;
- при нулевом количестве аспектов frame и registry сохраняются, текст остаётся
  пустым;
- если все документы группы удалены вручную, registry очищается и виджет не
  создаётся заново без явного «Разместить на столе».

Frame должен иметь собственные `part` и `ownerType`, а не определяться по
тексту или координатам. Это также позволит безопасно удалять только документы
конкретной группы.

### 7. Синхронизация и хуки

Реализовать `syncSituationAspects(scene = canvas?.scene)`:

1. Прочитать и нормализовать системный флаг.
2. Найти registry и документы по `widgetId`.
3. Если registry отсутствует, ничего не создавать автоматически.
4. Если registry есть, обновить text Drawing: текст, размеры, шрифт, цвет,
   ADT-флаги, координаты, frame и background Drawing.
5. Создать отсутствующий документ группы или удалить лишний только по его
   флагам.
6. Синхронизировать фон отдельно от текста: изменить его fill/texture, размеры,
   elevation и sort без изменения anchor.
7. При ручном удалении всей группы очистить module registry.

Подключить следующие источники обновления:

- `updateScene`, когда изменяется
  `flags.fate-core-official.situation_aspects`;
- `canvasReady`;
- изменение настроек виджета через `updateSetting`;
- успешное сохранение в менеджере;
- `Hooks.on("chars-to-table.newScene", ...)` от `FatePointManager`.

Синхронизацию событий сцены debounce-ить, чтобы одно сохранение не вызывало
несколько последовательных update одного Drawing. При изменении аспекта извне
виджет должен обновляться, если он уже размещён, но сам факт наличия флага не
должен создавать новый виджет.

### 8. Размещение, drag и взаимодействие

1. «Разместить на столе» вызывает `PlacementManager.placeGroup` с текущими
   документами, frame bounds и локализованным label.
2. При подтверждении создать text/frame одним `widgetId`, затем записать
   `scene.flags["chars-to-table"].situationAspectsWidget`.
3. При переразмещении сначала запросить подтверждение, удалить только старую
   группу и registry, затем запустить placement заново.
4. Групповой drag должен сдвигать text и frame и обновлять scene anchor через
   общую ветку scene-owned widgets в `widgetDrag`.
5. Добавить действие «Убрать со стола» с подтверждением. Системный массив
   аспектов при этом не удалять.
6. Двойной клик по группе открывает полноценное меню управления аспектами только
   для GM. У игрока виджет остаётся доступным для просмотра, но его двойной
   клик не даёт редактировать scene flag.
7. Не добавлять в первую итерацию кликабельные invoke-боксы на самом Drawing:
   изменение invoke выполняется в менеджере, чтобы не зависеть от hit-test
   отдельных строк текста.

### 9. Настройки

Зарегистрировать штатные world settings с дефолтами исходного макроса:

- ширина виджета: `500`;
- высота виджета: `800`;
- семейство шрифта: `BadScript`, если оно зарегистрировано, иначе фолбэк
  `Montserrat`;
- размер шрифта: `32`;
- цвет текста: `#000000`.

Добавить отдельную настройку фона ситуативных аспектов:

- `situationAspectsBackgroundTexture` — текстура подложки, пустое значение
  означает обычную заливку;
- при необходимости `situationAspectsBackgroundColor` и
  `situationAspectsBackgroundAlpha`, если стандартной белой заливки виджета
  персонажа недостаточно.

Настройка `backgroundTexture` персонажа не должна использоваться как fallback:
пустая текстура аспектов должна означать самостоятельный дефолтный фон
аспектов, а не наследование фона actor-widget. File picker для нового поля
должен работать отдельно, но по тому же механизму, что и текущий picker.

Позиционные настройки `widgetPositionX/Y` из журнала не переносить: положение
определяется placement-flow и хранится в scene registry. Изменение размера,
шрифта, цвета или отдельного фона должно обновлять уже размещённый виджет и
сохранять anchor.
Для выбора шрифта и цвета переиспользовать текущую обработку
`renderSettingsConfig`.

### 10. Интеграция с «Новой сценой»

`FatePointManager.executeNewScene` уже:

- записывает выбранные аспекты в
  `fate-core-official.situation_aspects`;
- вызывает `Hooks.callAll("chars-to-table.newScene", ...)`.

Менеджер аспектов должен подписаться на этот hook. Если виджет существует на
сцене, он обновляется из нового массива. Если виджет не размещён, новый Drawing
не создаётся. Это сохраняет разделение между состоянием сцены и его визуальным
представлением.

После завершения операции «Новая сцена» должны быть видны выбранные аспекты и
их исходные `free_invokes`; удалённые из новой сцены элементы не должны
оставаться в тексте виджета.

### 12. Критерии готовности

- Добавление, переименование, удаление и изменение invoke корректно меняют
  `fate-core-official.situation_aspects`.
- Значение `free_invokes` не становится отрицательным и не конкатенируется как
  строка.
- Отмена диалога не меняет scene flag и документы сцены.
- Размещённый виджет обновляется после сохранения, внешнего `updateScene`,
  `canvasReady`, изменения настроек и «Новой сцены».
- Системный flag без registry не создаёт Drawing сам по себе.
- Перетаскивание text или frame двигает всю группу и сохраняется после reload.
- Фон аспектов настраивается и обновляется независимо от
  `backgroundTexture` виджета персонажа и фона GM FP.
- Двойной клик GM по любой части группы открывает меню со списком аспектов,
  `+`/`−` invoke, добавлением, переименованием и удалением; изменения доходят
  до системного scene flag и виджета.
- Удаление виджета не удаляет массив аспектов.
- Старые Drawing с `core.situationAspectsWidget` не удаляются автоматически.
- GM может редактировать состояние, игроки видят виджет, но не получают GM-only
  инструменты.
- Проверено в Foundry v14 с включённым Advanced Drawing Tools.

## Зафиксированные решения

- **Представление на сцене**: группы состоят из отдельных `Drawing` + `Tile`, а
  не из одной растеризованной картинки. Это даёт нативное редактирование и
  дешёвый автосинк.
- **Actor-widget**: actor-owned документы используют `actorUuid` и реестр
  `actor.flags["chars-to-table"].widgets`.
- **Scene-widget**: GM FP и ситуативные аспекты используют `ownerType`,
  scene registry и не требуют `actorUuid`.
- **Источники данных**: FP игрока хранится в actor system data, FP мастера — в
  совместимом системном user flag, ситуативные аспекты — в системном scene
  flag `fate-core-official.situation_aspects`.
- **Раскладка**: шаблоны находятся в `layouts.js`, координаты относительны
  anchor. Для персонажа anchor — верхний левый угол портрета.
- **Интерактив**: placement, автосинк и групповой drag входят в базовую
  инфраструктуру; кликабельные игровые элементы добавляются отдельными
  фичами.
- **Настройки**: новые функции используют штатные `game.settings`, а не
  JSON-страницы журнала старого набора макросов.
- **Шрифты**: используются только зарегистрированные в
  `CONFIG.fontDefinitions`; незарегистрированный шрифт заменяется на
  Montserrat с предупреждением.
- **Legacy-объекты**: старые документы макросов не удаляются автоматически без
  явной процедуры миграции.

## Ключевые технические решения

### Идентификация групп

- Actor-widget:
  `flags["chars-to-table"] = { widgetId, part, index, actorUuid }`.
- GM scene-widget:
  `flags["chars-to-table"] = { widgetId, part, index, ownerType: "gm" }`.
- Situation aspect scene-widget:
  `flags["chars-to-table"] = { widgetId, part, index, ownerType: "situationAspects" }`.
- Осиротевшие записи очищаются только по module flags и registry; поиск по
  содержимому текста Drawing не используется.

### Формат темплейта персонажа

```js
{
  id: "default",
  scale: 1,
  drawingOffset: { x: -135, y: -150 },
  bounds: { stroke: 1, alpha: 0.2, ... },
  elements: [
    { id: "portrait", type: "tile", content: "@portrait", x: 0, y: 0, w: 270, h: 270 },
    { id: "name", type: "drawing", content: "@name", matchBoundsWidth: true },
    { id: "skillName", type: "drawing", rows: "@skillNames", stroke: 2, lineHeight: 68 },
    { id: "fatePointTokens", type: "tileRow", content: "@fatePointTokens", step: 20 }
  ]
}
```

Типы элементов: `tile`, `tileRow`, `drawing`. `stroke` задаёт обводку,
`weight` — font weight для ADT, `matchBoundsWidth` — ширину по реальным bounds
виджета. Резолверы включают `@name`, `@portrait`, `@aspects`, `@skillNames`,
`@skillValues`, `@fatePointTokens` и заголовки через i18n.

### Placement и автосинк

- Placement использует DOM-события `pointermove`/`pointerdown` на
  `canvas.app.view`, потому что PIXI-события могут перехватываться Foundry.
- Координаты получают через inverse world transform с fallback на local position.
- Коммит создаёт документы batch-запросами и сохраняет registry после успешного
  создания.
- `updateActor` вызывает actor-widget sync с debounce 400 мс.
- `canvasReady` выполняет реконсиляцию actor-widget и синхронизацию scene-owned
  групп.
- Обновления, инициированные синком, помечаются `charsToTableSync`, чтобы не
  запускать рекурсивный групповой drag.

### Advanced Drawing Tools

Текстовые Drawing получают ADT-флаги с `dropShadow: false`,
`strokeThickness: 0`, `align` и при необходимости `fontWeight`.
